# Security and user controls

Chista is a local-first desktop evidence tool. Imported files, telemetry, connector results and model responses are untrusted data. Automatic redaction is best effort: review every outbound preview. No subscription is required for local debugging, redaction, approvals or export. There is no payment processor, billing state, subscription check or feature gate.

## HTTP requests

`chista_http_request` accepts only structured HTTP(S) requests without URL credentials. It has no shell interpolation, file input, curl config loading, proxy inheritance or automatic retries. All methods, including GET, need a one-call approval showing the sanitized URL, method, headers and body. Agent messages cannot grant an approval.

Before connecting, native code resolves the host, rejects non-public IPv4/IPv6 answers (including mapped IPv4, loopback, private, link-local, multicast, transition, documentation and metadata address ranges), and pins curl to a validated IP with `--resolve`. This avoids a second DNS lookup and DNS rebinding between validation and connection. Every DNS answer must be permitted. TLS certificate checks stay enabled. Redirect responses are rejected; following a Location requires a separate reviewed request.

Limits: URL 8,192 bytes; 30 request headers, 16 KB aggregate; header names 100 bytes and values 8,192 bytes; text body 100,000 bytes; response 1 MB; response headers 16 KB; DNS wait 5 seconds; connect 10 seconds; curl 30 seconds; process watchdog 35 seconds, plus DNS time. Responses are monitored every 10 ms. Content-Length/transfer/hop-by-hop/Host/proxy headers and CR/LF/NUL injection are rejected. Non-text responses are omitted. Response header monitoring may transiently overshoot its threshold before the process is killed. A timed-out platform DNS call may finish in its background thread; its result cannot cause a connection.

Workspace configuration supports exact HTTP(S) origin exceptions for local debugging. Approving `http://127.0.0.1:8080` does not approve another port, scheme or hostname. Exceptions permit private destinations, including sensitive local services, only for that workspace. They expire at exit and do not enable redirects. Clearing them and applying the policy revokes access and closes native sessions. Hosted model connections are separately user-configured HTTPS endpoints, use no redirects, and use the existing hosted transport; the curl destination policy does not cover that transport.

## CLI and MCP boundaries

Chat agents run in an isolated temporary directory with no selected repository path or raw source content. Selected repository display names and reviewed sanitized excerpts are the project context. Shell and filesystem tools are unavailable; Codex uses a read-only filesystem/no-network permission profile and disables plugins, hooks, shell, web search and other unrelated tools. Claude uses only tool discovery and the controlled MCP bridge; other built-in tools are denied. This intentionally preserves the existing evidence-only chat model.

MCP servers start disabled by default. In Workspace configuration, preview native startup commands, arguments and endpoints, then approve exact `codex:server-name` or `claude:server-name` entries. Only reviewed startup configurations can be enabled; changes to command, arguments, environment, endpoint or headers require another preview and approval. Claude strict MCP configuration prevents implicit company/global connector discovery from bypassing this selection. Each MCP invocation additionally requires one-call approval and local result sanitization, even if the tool advertises itself as read-only. Unknown tool names, duplicate calls, late/expired responses and unsupported permission requests fail closed. Policy changes close native sessions; reconnect the chat before continuing.

**External connector limitation:** a stdio MCP process runs with the user's OS account privileges and remote MCP services enforce their own project scope. A working directory or read-only tool annotation is not a sandbox for arbitrary external code. Approve only trusted connectors configured for the selected project. Their startup can make network connections; review grants that startup permission. Chista cannot prove that a remote tool is read-only or undo its side effects. No autonomous repository-writing shell workflow is provided.

## Credentials

Chista-managed provider tokens use macOS Keychain, Windows Credential Manager, or the platform Secret Service through `keyring`. MCP credentials can be stored per workspace/server as JSON containing `env` and/or `http_headers` string maps in Workspace configuration. Credential environment names must end in TOKEN, KEY, SECRET, PASSWORD, CREDENTIALS or ACCESS_KEY_ID; execution environment overrides belong in the separately reviewed native connector configuration. Header injection and routing overrides are rejected. Credentials are injected natively into approved connectors. Clear/Delete removes the OS entry; reconnect after changes. Failure to use the credential store produces an error; there is no plaintext fallback. Tokens are cleared from form state after successful save and never enter localStorage, investigation bundles or audit records. Transient input/request memory necessarily contains credentials during use. OS access controls govern other processes running as the same user.

Existing CLI-owned credentials and sign-in are still managed by the CLI. Chista does not rewrite or delete users' native CLI configuration. Avoid credentials in CLI command arguments; use the credential store instead. Native integration may require private temporary settings/MCP files containing credentials for the life of a session (0600 on Unix, in a private temporary directory; removed on normal teardown). Abrupt OS/process termination can leave temporary files. This is a remaining limitation of the CLI transport, not durable investigation storage. Imported legacy CLI secrets are not automatically migrated.

## Generated UI and imports

Model JSON passes bounded Zod schemas before it becomes a locally generated OpenUI program. Only registered components are available. Strings are encoded with JSON.stringify, and React renders evidence/code/HTML-looking text as text. There is no arbitrary HTML, script, eval, remote component loading or execution of code blocks. CSP restricts scripts to bundled application code. Malformed generated UI falls back to plain text.

Imports accept text CSV/TSV/JSON/JSONL/NDJSON/log files, at most 20 artifacts and 2 MB per file. JSONL/NDJSON is parsed into JSON before sanitization. Sentry event JSON and OpenTelemetry OTLP JSON/attribute arrays use this local import path; no Sentry credentials or automatic remote telemetry fetch are needed. Sensitive OTel attribute keys are recognized before values reach context. Custom profiles add exact sensitive terms to artifacts, composer and tool sanitization. Review remains essential: proprietary secret formats and information embedded under unexpected keys can be missed. Sanitization also changes tool arguments, which can make a request fail.

## Saved investigations, sharing and audit

Encrypted `.chista` files use AES-256-GCM with a fresh 16-byte salt and 12-byte nonce, PBKDF2-SHA256 with 600,000 iterations, and authenticated format metadata. A user-supplied passphrase (12–1,000 characters) is never persisted. There is no recovery service. Investigation saves contain sanitized context/evidence and bounded chat excerpts (up to 10 sessions, 40 messages each, 80,000 characters total; truncation is marked) and optionally refreshed audit metadata, never original files or reversal mappings. Encrypted profiles contain exact custom redaction values. Decrypted files are schema-validated, treated as untrusted and sanitized again; reopening never automatically submits them to an agent. Files stay wherever the user saves them and can be deleted using the OS. No automatic cloud sync occurs.

Share bundles whitelist sanitized excerpts, generic artifact identifiers and minimal audit metadata. The UI previews the exact bytes, requires a separate review checkbox, and downloads JSON for manual sharing. It creates no public URL or upload. Native audit history has a read-only API and no edit/delete UI: the latest 2,000 agent/HTTP/MCP events per workspace stay in memory until exit. It stores sequence/time/action/state, excluding prompts, arguments, credentials, raw results, tool labels and paths. Refresh to include it in a saved/exported bundle. It is a local operational history, not a durable, independently verifiable compliance ledger.

The Free/Pro/Team capability catalog is planning metadata only. Every shipped capability is available without a subscription; no billing is invented.

## Release signing

Release CI fails if required signing secrets are missing, imports certificates into temporary runner stores, signs installers, checks signatures/notarization, and removes signing material. Never commit certificates, passwords or generated signing configuration. See [RELEASING.md](RELEASING.md) for setup. Windows/macOS signing must be exercised with real CI secrets before claiming a trusted release.

## Playbooks, checklists and branches

Playbooks are registered instruction templates, expanded before normal prompt sanitization and optional outgoing review. No native skill discovery, shell, plugin execution or additional permissions are enabled. Untrusted task reports pass bounded strict schemas, can address only existing steps, and cannot alter tools or permissions. Unsupported completion citations are blocked, and supported reports remain explicitly agent-reported. Manual plan changes invalidate outstanding request previews.

Branch checkpoints are in-memory snapshots of a sanitized conversation prefix, selected context, available sources, task state and a private copy of the redaction profile/mappings. The latest 100 message checkpoints per session can be used. A branch has a fresh native conversation and keeps the current workspace's security policy; it never restores old permissions or pending approvals. No action is replayed by creating a branch and external side effects cannot be rewound. Sensitive reversal mappings in checkpoint memory never enter an outbound request or share bundle.
